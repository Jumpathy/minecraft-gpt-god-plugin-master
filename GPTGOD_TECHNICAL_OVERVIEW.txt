================================================================================
  1. HIGH-LEVEL ARCHITECTURE
================================================================================

GPTGOD is a Paper MC plugin (1.20.4) that runs a periodic "god loop" every N
seconds (default: 40). During each cycle, all player actions collected since the
last cycle are bundled into a text log and sent to an LLM (OpenAI GPT-4o or
Anthropic Claude). The LLM responds with structured tool/function calls that
execute Minecraft actions (lightning strikes, item drops, entity spawns, etc.)
and optionally sends voice or text messages to players.

The architecture has three major layers:

  [Minecraft World] → [Event Logging] → [LLM API] → [Function Execution]

Key design choices:
  - Two separate API instances run per cycle: one for ACTIONS and one for SPEECH.
    This prevents the god from only talking or only acting.
  - All API calls are asynchronous. Minecraft game logic is never blocked.
  - Events are pre-tokenized and combined to stay within LLM token limits.
  - The god has a randomly generated personality that persists for the session.
  - Supports two game modes: SANDBOX (free play) and DEATHMATCH (team combat).
  - Supports both OpenAI GPT and Anthropic Claude models via a common API interface.

Main source files:
  GPTGOD.java               — Plugin entry point, lifecycle management
  GameLoop.java             — Periodic scheduler, orchestrates each god cycle
  EventLogger.java          — Central repository for all logged events
  LoggableEventHandler.java — Bukkit event listeners that create Loggable objects
  GPT/GptActions.java       — All functions the god can execute
  GPT/GptAPI.java           — OpenAI HTTP client
  GPT/ClaudeAPI.java        — Anthropic HTTP client
  GPT/Personality.java      — Random personality generation
  GPT/Prompts.java          — System prompt management
  GPT/SummarizeLogs.java    — Async historical summarization
  GPT/GenerateCommands.java — Converts natural language to Minecraft commands
  StructureManager.java     — Tracks player-built structures
  RoundSystem.java          — DEATHMATCH round and world reset logic
  WorldManager.java         — World loading/unloading/restoration
  ServerInfoSummarizer.java — Generates snapshot of current server state


================================================================================
  2. THE CORE GAME LOOP
================================================================================

Class: GameLoop.java
Scheduler: Bukkit repeating task, period = config.rate seconds (default 40s)

Each cycle executes a class called GPTTask (implements Runnable). The steps are:

  STEP 1 — Calculate token budget
    - staticTokens   = tokens in (system prompt + personality text)
    - summaryTokens  = tokens in the current historical summary (if any)
    - toolTokens     = tokens in the tool definitions being sent this cycle
    - nonLogTokens   = staticTokens + summaryTokens + toolTokens + 2 (role markers)
    - logBudget      = modelTokenLimit - nonLogTokens

  STEP 2 — Cull events
    EventLogger.cull(logBudget) removes oldest events from the log until the
    remaining events fit within the logBudget.

  STEP 3 — Dump events
    EventLogger.dump() returns the formatted event log as a single string and
    triggers async summarization of old events to preserve historical context.

  STEP 4 — Build server status snapshot
    ServerInfoSummarizer generates a snapshot including:
      - Each online player's health, inventory, location, nearby danger level
      - Time of day, weather, active objectives
      - Structures registered in StructureManager
      - Team assignments (DEATHMATCH mode)

  STEP 5 — Select action tools for this cycle
    GPTUtils.randomToolSubset() selects 3 random non-speech tools from the
    full function pool. The "command" function is always included (persistent).
    This prevents the god from always using the same actions.

  STEP 6 — Fire two async API calls in parallel
    ACTION API:
      - System prompt: personality + action instructions
      - User message: server snapshot + event log
      - Tools: 3 random action tools + "command" (persistent)
      - Goal: reward/punish players via function calls

    SPEECH API:
      - System prompt: personality + speech instructions
      - User message: same server snapshot + event log
      - Tools: whisper, announce, setObjective, clearObjective only
      - Goal: communicate with players, set goals

  STEP 7 — Process responses (main thread)
    GptActions.processResponse() parses each tool_call from the response and
    dispatches the corresponding lambda. All Bukkit API calls are scheduled
    on the main server thread via Bukkit.getScheduler().runTask().

  STEP 8 — Log god actions
    Each executed function creates a GPTActionLoggable that is added back to
    EventLogger so the god's history includes its own past actions.

Token calculation is critical. If the log is too large, the API returns an error.
The plugin eagerly calculates tokens for every event as it is created (not at
send time) so the cull step is fast.


================================================================================
  3. EVENT TRACKING — WHAT THE GOD OBSERVES
================================================================================

All event listening lives in LoggableEventHandler.java, which registers ~30
Bukkit event handlers. Each handler creates one or more Loggable objects and
passes them to EventLogger.addLoggable().

Below is the complete list of tracked events:

--- COMMUNICATION ---

  AsyncPlayerChatEvent
    Triggers: Player sends a chat message
    Loggable: ChatLoggable
    Log format: "[timestamp] <PlayerName> said: <message>"
    Combinable: Yes — multiple chats by same player merge into one entry

  VoiceChatEvent (Simple Voice Chat plugin)
    Triggers: Player speaks in voice chat (after Whisper transcription)
    Loggable: ChatLoggable (same class, marked as voice)
    Log format: "[timestamp] <PlayerName> said (voice): <transcribed text>"

--- COMBAT AND DAMAGE ---

  EntityDamageByEntityEvent
    Triggers: A player attacks another entity (player or mob)
    Loggable: AttackLoggable
    Log format: "[timestamp] <PlayerName> attacked <TargetName> with <ItemName>
                 for <damage> damage"
    Combinable: Yes — multiple attacks by same player on same target with same
                weapon are combined; hit count and damage accumulated

  EntityDamageEvent
    Triggers: A player takes damage (not from another entity)
    Loggable: DamageLoggable
    Log format: "[timestamp] <PlayerName> was damaged by <DamageCause>"
    Combinable: Yes — repeated damage from same source accumulates

  PlayerDeathEvent
    Triggers: A player dies
    Loggable: DeathLoggable
    Log format: "[timestamp] <death message from Minecraft>"

  EntityDeathEvent
    Triggers: A player kills an entity
    Loggable: KillLoggable
    Log format: "[timestamp] <PlayerName> killed <EntityType>"
    Filter: Skips kills of common/trivial entities (squid, cod, salmon, etc.)
            Only logs kills of monsters, bosses, and animals

  EntityCombustByEntityEvent
    Triggers: An entity sets a player on fire
    Loggable: CombustLoggable
    Log format: "[timestamp] <PlayerName> was set on fire by <CombusterName>"

--- INVENTORY AND ITEMS ---

  EntityPickupItemEvent
    Triggers: Player picks up an item from the ground
    Loggable: ItemPickupLoggable
    Log format: "[timestamp] <PlayerName> picked up <count>x <ItemName>"
    Combinable: Yes — pickups of same item by same player are merged

  PlayerDropItemEvent
    Triggers: Player drops an item
    Loggable: DropItemLoggable
    Log format: "[timestamp] <PlayerName> dropped <count>x <ItemName>"
    Combinable: Yes — drops of same item by same player are merged

  CraftItemEvent
    Triggers: Player crafts an item in a crafting table or inventory
    Loggable: CraftLoggable
    Log format: "[timestamp] <PlayerName> crafted <count>x <ItemName>"
    Combinable: Yes

  FurnaceSmeltEvent
    Triggers: A furnace completes smelting (attributed to nearest player)
    Loggable: CraftLoggable (reused for smelting)
    Log format: "[timestamp] <PlayerName> smelted <count>x <ItemName>"

  PlayerItemConsumeEvent
    Triggers: Player eats food or drinks a potion
    Loggable: EatingLoggable
    Log format: "[timestamp] <PlayerName> ate/drank <ItemName>"

  PrepareAnvilEvent
    Triggers: Player renames an item in an anvil
    Loggable: RenameItemLoggable
    Log format: "[timestamp] <PlayerName> renamed <OriginalName> to <NewName>"
    Note: Implements UserInputLoggable for content moderation hooks

--- BUILDING AND WORLD INTERACTION ---

  BlockPlaceEvent
    Triggers: Player places a block
    Two paths:
      a) Special blocks: Chest, Furnace, Enchanting Table, Beacon, Anvil,
         Brewing Stand, Jukebox, Note Block, TNT, Bed, Respawn Anchor,
         Crafting Table, Barrel, Smoker, Blast Furnace, Lectern, Grindstone,
         Lodestone, Conduit, Beacon → logs SpecialBlockPlaceEventLoggable
      b) All other blocks → no loggable created (too noisy)

    SpecialBlockPlaceEventLoggable format:
      "[timestamp] <PlayerName> placed a <BlockType> at <X,Y,Z>
       (near structure: <StructureName>)" [if near a tracked structure]

  SignChangeEvent
    Triggers: Player finishes writing on a sign
    Loggable: WriteOnSignLoggable
    Log format: "[timestamp] <PlayerName> wrote on a sign: <line1> <line2> ..."
    Note: Implements UserInputLoggable for content moderation hooks

  NameTagEvent / EntityInteractEvent (via anvil rename)
    Triggers: Player names an entity with a name tag
    Loggable: RenameEntityEvent
    Log format: "[timestamp] <PlayerName> named a <EntityType>: <NewName>"
    Note: Implements UserInputLoggable for content moderation hooks

  PlayerInteractEvent
    Triggers: Player right-clicks a block or uses an item
    Loggable: InteractLoggable
    Log format: "[timestamp] <PlayerName> used <ItemName> on <BlockType>"
    Combinable: Yes — repeated interactions of same type are merged with count

  PlayerInteractEntityEvent
    Triggers: Player right-clicks an entity
    Loggable: UseLoggable
    Log format: "[timestamp] <PlayerName> interacted with <EntityName>"

--- ENVIRONMENT AND ANIMALS ---

  PlayerFishEvent
    Triggers: Player catches something while fishing
    Loggable: FishingLoggable
    Log format: "[timestamp] <PlayerName> caught a <EntityType/ItemName>"

  EntityBreedEvent
    Triggers: Two animals breed (triggered by a player)
    Loggable: EntityLoveLoggable
    Log format: "[timestamp] <PlayerName> bred two <AnimalType>s"

  EntityTameEvent
    Triggers: Player tames an animal (wolf, horse, cat, etc.)
    Loggable: TameAnimalLoggable
    Log format: "[timestamp] <PlayerName> tamed a <AnimalType>"

  VehicleEnterEvent / EntityMountEvent
    Triggers: Player mounts an entity (horse, boat, minecart, pig)
    Loggable: MountLoggable
    Log format: "[timestamp] <PlayerName> mounted a <EntityType>"

  EntityPlantEvent / BlockFertilizeEvent
    Triggers: Player plants crops or uses bone meal
    Loggable: PlantLoggable
    Log format: "[timestamp] <PlayerName> planted <CropType>"
    Combinable: Yes — repeated plantings by same player merged

--- PROGRESSION ---

  PlayerAdvancementDoneEvent
    Triggers: Player completes a Minecraft advancement
    Loggable: AchievementLoggable
    Log format: "[timestamp] <PlayerName> earned the advancement: <Title>
                 (<Description>)"
    Filter: Skips recipe unlock advancements (too common)

  PlayerBedEnterEvent
    Triggers: Player gets into a bed to sleep
    Loggable: GenericEventLoggable
    Log format: "[timestamp] <PlayerName> went to sleep"

--- GOD ACTIONS (self-logged) ---

  GPTActionLoggable
    Created when the god executes any function
    Log format: "[timestamp] God performed: <action description>"
    Purpose: Gives the god memory of its own past actions


================================================================================
  4. THE LOGGABLE SYSTEM — HOW EVENTS ARE REPRESENTED
================================================================================

All events implement the Loggable interface:

  interface Loggable {
    String getLog();             // Text sent to GPT
    Loggable combine(Loggable);  // Merge with similar event (return null if not mergeable)
    Instant getRawInstant();     // Event timestamp
    int getTokens();             // Pre-calculated token count
    void resetTokens();          // Invalidate token cache
  }

All concrete loggables extend BaseLoggable, which provides:
  - Timestamp storage and formatting: "HH:mm:ss" format
  - Token caching: calls GPTUtils.countTokens(getLog()) on first access
  - Default combine(): returns null (events cannot be merged by default)

The getLog() string is the only thing the LLM sees about each event.
It is designed to be human-readable natural language so the LLM can understand
player behavior without needing Minecraft-specific knowledge.

Example log output from a sequence of events:
  "12:34:01 Steve said: let's go mining
   12:34:15 Steve picked up 3x iron_ore
   12:34:22 Steve attacked Skeleton with Diamond Sword for 6.0 damage
   12:34:23 Steve attacked Skeleton with Diamond Sword for 6.0 damage
   12:34:24 Steve killed Skeleton
   12:34:45 Steve crafted 4x iron_ingot
   12:35:01 Alex earned the advancement: Getting an Upgrade (Obtain a smithing table)"


================================================================================
  5. EVENT COMBINATION AND TOKEN BUDGET MANAGEMENT
================================================================================

--- EVENT COMBINATION ---

When EventLogger.addLoggable(newEvent) is called, it first scans the existing
event log for a recent event of the same type and calls combine(). If combine()
returns a non-null Loggable, the old event is replaced by the merged one.

Combination rules by loggable type:
  - AttackLoggable: same attacker + same target + same weapon → accumulate damage and hits
  - ItemPickupLoggable: same player + same item type → accumulate count
  - DropItemLoggable: same player + same item type → accumulate count
  - CraftLoggable: same player + same item type → accumulate count
  - PlantLoggable: same player + same plant type → accumulate count
  - DamageLoggable: same entity + same damage cause → accumulate damage
  - ChatLoggable: same player → concatenate messages
  - InteractLoggable: same player + same block + same item → accumulate count
  - UseLoggable: same player + same block + same item + same action → accumulate

This can dramatically reduce token usage for repetitive actions like mining,
farming, or sustained combat.

--- TOKEN BUDGET ---

Token counting uses the JTOKKIT library with CL100K_BASE encoding, which matches
the tokenizer used by OpenAI GPT-4 models. Each Loggable pre-calculates its
token count when first accessed and caches it. Combination invalidates the cache.

EventLogger maintains a running total: totalTokens.

EventLogger.cull(budget) removes events from the TreeSet (sorted oldest-first)
until totalTokens <= budget. Oldest events are dropped first.

EventLogger.dump() returns the remaining events as a single concatenated string
and triggers SummarizeLogs.summarize() asynchronously on the events being dropped
during the next cull, building a running summary of older history.

--- SUMMARY SYSTEM ---

SummarizeLogs sends dropped events to GPT with the following prompt:
  "You are an AI summarizer. Summarize the following Minecraft game logs
   while preserving plot, player reputation, and any objectives mentioned.
   Write in past tense."

The resulting summary is stored and included in future API calls before the
live event log. This gives the god long-term memory without exceeding token limits.

Budget accounting with summary:
  nonLogTokens = staticTokens + summaryTokens + toolTokens + 2
  logBudget    = modelLimit - nonLogTokens


================================================================================
  6. THE GOD'S PERSONALITY
================================================================================

At plugin startup, Personality.java generates a random set of behavioral
preferences from the potentialBehaviors list in config.yml.

Process:
  1. Shuffle potentialBehaviors list
  2. Take first N as liked behaviors (default N=3)
  3. Take next M as disliked behaviors (default M=3)
  4. Construct a personality briefing string

Personality briefing format:
  "You have a unique personality. You enjoy when players: <list of liked behaviors>.
   You dislike when players: <list of disliked behaviors>.
   React accordingly when you observe these behaviors."

This briefing is inserted into the system prompt for every API call. The
personality is fixed for the entire server session (until restart or plugin reload).

Example liked behaviors from config defaults:
  - build elaborate structures
  - cooperate with other players
  - explore dangerous areas
  - engage in combat
  - farm and gather resources

Example disliked behaviors:
  - stand idle for long periods
  - destroy their own structures
  - avoid combat
  - waste resources


================================================================================
  7. HOW EVENTS ARE FORMATTED INTO API CALLS
================================================================================

--- SYSTEM PROMPT (ACTION API) ---

  "{personalityBriefing}

   You are an all-powerful god observing a Minecraft world. Use your tools to
   reward players whose behavior you enjoy and punish players whose behavior
   you dislike. You can only interact through the provided tools.

   [Mode-specific instructions: SANDBOX or DEATHMATCH]"

--- SYSTEM PROMPT (SPEECH API) ---

  "{personalityBriefing}

   You are an all-powerful god. Use whisper to speak privately to players or
   announce to address all players. You may also set or clear objectives.
   Speak in character as a divine entity. Be dramatic, brief, and impactful."

--- USER MESSAGE (both APIs) ---

  The user message is a combination of:

  Part 1 — Server snapshot (from ServerInfoSummarizer):
    "=== Current Server State ===
     Time: <in-game time, e.g., 'Noon'>
     Weather: <Clear/Rain/Thunder>

     Players:
       <PlayerName> — Health: <hp>/20.0, <danger level>
         Armor: <helmet, chestplate, leggings, boots>
         Holding: <item in hand>
         Nearby enemies: <count>

     Active Objectives:
       - <objective text>

     Known Structures:
       - <StructureName> at <X,Y,Z>

     Teams (DEATHMATCH):
       Red Team: <player names>
       Blue Team: <player names>"

  Part 2 — Event log (from EventLogger.dump()):
    "=== Recent Events ===
     <historical summary if exists>

     <live event log>"

  The combined user message is sent as a single "user" role message.

--- REQUEST BODY STRUCTURE ---

  OpenAI format:
  {
    "model": "gpt-4o",
    "messages": [
      { "role": "system", "content": "<system prompt>" },
      { "role": "user",   "content": "<server snapshot + event log>" }
    ],
    "tools": [
      {
        "type": "function",
        "function": {
          "name": "smite",
          "description": "Strike a player with lightning as punishment",
          "parameters": {
            "type": "object",
            "properties": {
              "playerName": {
                "type": "string",
                "description": "The name of the player to smite"
              },
              "power": {
                "type": "number",
                "description": "Lightning power (1-10)"
              }
            },
            "required": ["playerName", "power"]
          }
        }
      },
      ... (additional tools)
    ],
    "tool_choice": "auto"
  }

  Anthropic Claude format (ClaudeAPI):
  {
    "model": "claude-sonnet-4-6",
    "max_tokens": 1024,
    "system": "<system prompt>",
    "messages": [
      { "role": "user", "content": "<server snapshot + event log>" }
    ],
    "tools": [
      {
        "name": "smite",
        "description": "Strike a player with lightning as punishment",
        "input_schema": {
          "type": "object",
          "properties": { ... },
          "required": [ ... ]
        }
      },
      ...
    ]
  }

--- TOOL SELECTION PER CYCLE ---

  ACTION API tools (selected each cycle):
    - 3 randomly selected tools from the general action pool
    - "command" is always included (persistent)
    - Speech tools (whisper, announce) are excluded from action tool pool
    - Randomization prevents the god from always using the same 3 tools

  SPEECH API tools (fixed):
    - whisper
    - announce
    - setObjective
    - clearObjective

--- API RESPONSE HANDLING ---

  OpenAI response structure:
  {
    "choices": [{
      "message": {
        "role": "assistant",
        "tool_calls": [
          {
            "id": "call_abc123",
            "type": "function",
            "function": {
              "name": "smite",
              "arguments": "{\"playerName\": \"Steve\", \"power\": 5}"
            }
          }
        ]
      }
    }]
  }

  GptActions.processResponse() iterates tool_calls, looks up each function
  name in the functionMap (HashMap<String, Function<String>>), and calls
  the lambda with the JSON arguments string. Each lambda uses Gson to parse
  the arguments.


================================================================================
  8. OPENAI / CLAUDE API INTEGRATION
================================================================================

--- HTTP CLIENT ---

  GptAPI uses Apache HttpAsyncClient for non-blocking HTTP requests.
  All requests run on a dedicated ExecutorService thread pool.
  The main Minecraft server thread is never blocked.

  Endpoint: https://api.openai.com/v1/chat/completions
  Auth: Authorization: Bearer <openAiKey>
  Content-Type: application/json

  ClaudeAPI similarly uses async HTTP.
  Endpoint: https://api.anthropic.com/v1/messages
  Auth: x-api-key: <claudeApiKey>
  anthropic-version: 2023-06-01

--- MODEL SELECTION ---

  GPTModels.java factory:
    - If claudeApiKey is set in config → creates ClaudeAPI
    - Otherwise → creates GptAPI using gpt-model-name from config

  Supported models and token limits:
    OpenAI:
      gpt-4o          → 100,000 tokens (default)
      gpt-4o-mini     → 85,000 tokens

    Anthropic:
      claude-sonnet-4-6  → 100,000 tokens
      claude-haiku-4-5   → 100,000 tokens
      claude-opus-4-6    → 100,000 tokens

--- MESSAGE INDEX MANAGEMENT (GptAPI) ---

  GptAPI maintains a HashMap<String, Integer> to track the position of
  named messages in the messages array:
    "system"     → index of system prompt
    "logs"       → index of event log user message
    "summary"    → index of summary message (if exists)

  This allows in-place updates to specific messages (e.g., updating the
  log message) without rebuilding the full messages array each cycle.

--- DEBUGGING ---

  Set enabled: false in config to disable API calls while testing.
  Use /try <functionName> <jsonArgs> in console to test functions directly.
  Check server logs for "POSTING" lines that print the full request body.
  GptAPI.checkRequestBody() logs the request without sending.
  /tokens command shows prompt/completion token usage from last API calls.


================================================================================
  9. GOD FUNCTIONS — WHAT THE GOD CAN DO
================================================================================

All functions are defined in GptActions.java as lambdas stored in a
HashMap<String, Function<String>>. Each lambda receives a JSON string
of arguments and executes on the Bukkit main thread.

--- COMMUNICATION ---

  whisper(playerName: string, message: string)
    Sends a private chat message to the named player.
    If TTS enabled: generates audio via OpenAI TTS and plays to that player.
    Also whispers "(whisper)" prefix visually.

  announce(message: string)
    Broadcasts a message to all online players in chat.
    If TTS enabled: generates audio and plays to all players.
    Prefixed with a divine symbol (e.g., "[GOD]") in chat.

--- REWARDS ---

  giveItem(playerName: string, itemId: string, count: number)
    Adds items to the named player's inventory.
    itemId is a Minecraft material name (e.g., "diamond_sword", "golden_apple").
    Logs: "God gave <count>x <itemId> to <playerName>"

  summonSupplyChest(playerName: string, items: array, fullStacks: boolean)
    Spawns a chest at the player's feet filled with specified items.
    items: array of Minecraft material names.
    fullStacks: if true, fills each slot to max stack size.
    Logs: "God summoned a supply chest for <playerName>"

  revive(playerName: string)
    If the player is in spectator mode (dead in DEATHMATCH), switches them
    to survival mode and teleports them to their team's spawn.
    Logs: "God revived <playerName>"

  teleport(playerName: string, destination: string)
    Moves the player to a destination. Destination can be:
      - Another player's name → teleport to that player
      - A structure name → teleport to structure centroid
      - "spawn" → teleport to world spawn
    Logs: "God teleported <playerName> to <destination>"

--- PUNISHMENTS ---

  smite(playerName: string, power: number)
    Strikes the player with lightning. Power 1-10 scales damage.
    Power >= 5 also deals direct damage proportional to power.
    Logs: "God smote <playerName> with lightning (power <n>)"

  detonateStructure(structure: string, setFire: boolean, power: number)
    Creates an explosion at the centroid of the named structure.
    setFire: if true, ignites surrounding blocks.
    power: explosion radius (TNT = 4, Creeper = 3).
    Logs: "God detonated structure <name>"

--- OBJECTIVES ---

  setObjective(objective: string)
    Displays a goal on the Bukkit scoreboard sidebar (max 45 characters).
    Objectives expire after objectiveDecay minutes (default: 6).
    Logs: "God set objective: <text>"

  clearObjective(objective: string)
    Marks an objective as completed (changes display to strikethrough or removes).
    Logs: "God cleared objective: <text>"

--- WORLD MANIPULATION ---

  spawnEntity(position: string, entity: string, count: number, customName: string)
    Spawns entities at a location. Position can be:
      - "near <playerName>" → near that player
      - "at <structureName>" → at structure centroid
      - "X Y Z" coordinates
    entity: Minecraft EntityType name (e.g., "zombie", "ender_dragon").
    customName: optional display name for spawned entities.
    Logs: "God spawned <count>x <entity> at <position>"

  transformStructure(structure: string, block: string)
    Replaces every block in the named structure with the specified block type.
    block: Minecraft Material name (e.g., "obsidian", "gold_block").
    Executed block-by-block on the main thread.
    Logs: "God transformed structure <name> to <block>"

--- META ---

  command(prompt: string)
    The most flexible function. GPT provides a natural language description
    of what it wants to happen. GenerateCommands.generate() sends this to GPT
    again with context about player names, structures, and teams to produce
    actual Minecraft /commands. These commands are then executed via
    Bukkit's console command executor.

    Example prompt: "Summon 10 wither skeletons around Steve's position
                    and give them all enchanted iron swords"
    Result: Multiple /summon and /data commands executed on main thread.

    "command" is always included in action tools (persistent) to give the god
    maximum creative freedom for situations not covered by specific functions.

--- TOOL POOLS ---

  generalActionKeys (randomly selected 3 per cycle):
    giveItem, summonSupplyChest, revive, teleport, smite, detonateStructure,
    spawnEntity, transformStructure

  persistentActionKeys (always included in action tools):
    command

  speechActionKeys (only in speech API):
    whisper, announce, setObjective, clearObjective


================================================================================
  10. VOICE INTEGRATION (INPUT AND OUTPUT)
================================================================================

--- VOICE INPUT (Player → God) ---

  Requires: Simple Voice Chat plugin (voicechat-api 2.4.11)

  VoiceMonitorPlugin.java implements VoicechatPlugin and registers for
  microphone packet events from every connected player.

  Flow:
    1. Player speaks in Simple Voice Chat
    2. VoiceMonitorPlugin receives Opus-encoded audio packets
    3. OpusDecoder per player decodes to raw PCM audio
    4. PlayerAudioBuffer accumulates PCM samples
    5. After silence detection or buffer limit, buffer is finalized
    6. PCMtoWAV converts the buffer to WAV format (16kHz, 16-bit, mono)
    7. AudioFileManager writes temporary WAV file
    8. Transcription.java sends WAV to OpenAI Whisper API
       Endpoint: https://api.openai.com/v1/audio/transcriptions
       Model: whisper-1
       Language: from config (default: "en")
    9. Whisper returns transcribed text
   10. ChatLoggable created with transcription + timestamp
   11. Loggable added to EventLogger for next god cycle

  On player disconnect: OpusDecoder and AudioBuffer are cleaned up.

--- VOICE OUTPUT (God → Players) ---

  Enabled by: tts: true in config.yml
  Voice: configurable (default: "onyx") — OpenAI TTS voices

  TextToSpeech.java flow:
    1. whisper() or announce() function is called with a message
    2. If TTS enabled, TextToSpeech.synthesize(message, voice) is called
    3. HTTP POST to https://api.openai.com/v1/audio/speech
       Body: { "model": "tts-1", "input": "<message>", "voice": "<voice>" }
    4. Returns MP3 audio binary data
    5. Audio is broadcast via Simple Voice Chat's audio playback API
       - whisper(): played to only that player
       - announce(): played to all players in the world

  Players hear the god speaking in their headsets while also seeing the
  text in chat.


================================================================================
  11. WORLD AND ROUND MANAGEMENT
================================================================================

--- WORLD MANAGER ---

  WorldManager.java loads custom worlds from:
    plugins/gptgodmc/worlds/<worldName>/

  On load:
    1. FileUtils.copyDirectory() copies world files to a temporary active directory
    2. Bukkit.createWorld() loads the copied world
    3. Game rules set: mobGriefing=false, doWeatherCycle=false, doDaylightCycle=true
    4. Auto-save disabled on active world
    5. All online players teleported to world spawn
    6. Player inventories cleared, health reset

  On reset (triggered by RoundSystem):
    1. Bukkit.unloadWorld() unloads the active world
    2. Active world directory deleted
    3. Fresh copy made from source world
    4. World reloaded
    5. All players repositioned

--- ROUND SYSTEM (DEATHMATCH MODE) ---

  RoundSystem.java manages the DEATHMATCH game cycle:

  Team Assignment:
    - Players assigned to Red or Blue team on join
    - Teams balanced by size
    - Team-colored leather helmets given with Binding Curse
    - Spawn locations configured per team

  Round Flow:
    1. Game starts with all players alive in survival mode
    2. PlayerDeathEvent → dead player set to spectator mode
    3. Kill tracked: which team lost a player
    4. Check victory condition: all players of one team dead?
    5. If yes → winning team announced → world reset begins

  World Reset Sequence:
    1. GameLoop stopped
    2. EventLogger cleared
    3. WorldManager restores world from backup
    4. StructureManager structures cleared
    5. Historical summary cleared
    6. GPT personality optionally regenerated
    7. Players shuffled and reassigned to teams
    8. All players given team helmets and teleported to spawns
    9. GameLoop restarted

--- SANDBOX MODE ---

  No teams, no rounds. Players respawn normally at world spawn.
  The god observes freely and acts on its own judgment.
  Objectives can be set but there is no win condition.


================================================================================
  12. STRUCTURE TRACKING
================================================================================

  StructureManager.java tracks player-built structures as groups of blocks.

  Tracking triggers:
    - BlockPlaceEvent: Add block vector to appropriate structure
    - BlockBreakEvent: Remove block vector, possibly split/merge structures
    - BlockFadeEvent: Natural decay removes blocks
    - BlockBurnEvent: Fire removes blocks
    - EntityExplodeEvent: Explosions remove blocks

  Structure building algorithm:
    When a block is placed:
      1. Check 3x3x3 neighborhood for existing structure blocks
      2. If adjacent to one structure: add block to that structure
      3. If adjacent to multiple structures: merge all into one
      4. If no adjacent structures: create new structure (if min size met)

  Structure naming:
    Auto-generated: "{BLOCK_TYPE}_Structure_{ID}"
    Example: "STONE_Structure_3", "OAK_LOG_Structure_7"

  Structure size threshold:
    Structures with fewer than 20 blocks are not tracked (configurable).
    This avoids tracking single blocks or tiny constructions.

  Structure info available to GPT:
    - Structure name (used in function calls)
    - Centroid location (X, Y, Z)
    - Block count
    - Builder player name
    - Which players are nearby

  In API calls, structures appear in the server snapshot:
    "Known Structures:
     - OAK_LOG_Structure_1 at (120, 64, -45), built by Steve, 234 blocks
     - STONE_Structure_2 at (88, 68, -12), built by Alex, 567 blocks"

  GPT function calls reference structures by exact name:
    detonateStructure("OAK_LOG_Structure_1", true, 4)
    transformStructure("STONE_Structure_2", "obsidian")
    teleport("Steve", "OAK_LOG_Structure_1")


================================================================================
  13. SCOREBOARD AND OBJECTIVES
================================================================================

  GptObjectiveTracker.java manages objectives displayed on the scoreboard sidebar.

  setObjective():
    - Creates a Bukkit objective on the sidebar scoreboard
    - Text trimmed to 45 characters maximum
    - Score set to objectiveDecay value (default: 6)
    - Displayed to all players

  Decay system:
    - Runs every 60 seconds via Bukkit repeating task
    - Each active objective score decremented by 1
    - When score reaches 0: objective removed from scoreboard

  clearObjective():
    - Immediately removes objective from scoreboard
    - Logs completion

  DEATHMATCH mode:
    - Team scores displayed on scoreboard
    - Team assignments shown with team colors
    - Kill counts tracked per team

  Objectives appear in the server snapshot sent to GPT:
    "Active Objectives:
     - Mine 64 diamonds [6 min remaining]
     - Build a nether portal [3 min remaining]"
